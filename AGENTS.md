# Правила работы над VibeSprint

## Приоритеты проекта

1. Работающая демонстрация
2. Полный основной пользовательский сценарий
3. Надёжность
4. Визуальная полировка
5. Ценные дополнительные возможности
6. Архитектурное совершенство

Проект рассчитан на 24-часовой хакатон. Предпочитайте минимальную реализацию, достаточную для надёжной демонстрации.

## Общие правила

- Перед изменениями изучайте относящиеся к задаче код и документацию.
- Сохраняйте узкую область задачи и следуйте существующим паттернам.
- Не рефакторите посторонний код и не переписывайте рабочий код ради стиля.
- Добавляйте зависимости только при реальной необходимости.
- Не изменяйте сгенерированные файлы и не переименовывайте посторонние файлы.
- Не создавайте коммиты и не отправляйте изменения без явного запроса.
- Выполняйте минимальную проверку, достаточную для задачи.
- Не удаляйте и не откатывайте чужие изменения в рабочем дереве.
- Если область задачи должна расшириться, сначала объясните необходимость изменения общих файлов.

## Бэкенд

- По возможности сохраняйте архитектуру Spring Boot: контроллер -> сервис -> репозиторий.
- Бизнес-логика должна находиться в сервисах, а не в контроллерах или интеграционных адаптерах.
- Используйте DTO на границах API; не возвращайте persistence-сущности напрямую.
- Любые изменения схемы базы данных выполняйте через Liquibase.
- Не добавляйте архитектурные слои без конкретной текущей причины.
- Spring Boot остаётся источником истины для Квестов, XP, уровней, наград и рейда.

## Фронтенд

- Используйте существующий стек: Vue 3, TypeScript, Quasar, Composition API и Axios.
- Используйте Pinia только для состояния, общего между страницами или обработчиками событий.
- Не добавляйте React, Tailwind, другой UI-фреймворк или библиотеку состояния.
- Переиспользуйте существующую структуру API-клиента и маршрутизатора.

## Совместная работа

Три разработчика могут одновременно использовать несколько AI-агентов. Обычная схема:

`одна цель -> один владелец -> одна ветка/worktree -> узкая область`

- Не редактируйте параллельно общие контракты, схему, маршрутизатор, глобальные стили и конфигурацию.
- Согласуйте DTO и payload событий до параллельной реализации.
- Если задаче неожиданно нужен общий файл вне её области, сообщите об этом до редактирования.
- Часто объединяйте небольшие стабильные изменения; основная ветка должна оставаться демонстрируемой.

Подробности: [docs/COLLABORATION.md](docs/COLLABORATION.md).

## Документация

- Каждый поддерживаемый Markdown-документ должен содержать менее 200 строк.
- `docs/intial-plan.md` — сохранённый исходный бриф: не переименовывайте, не дополняйте и не используйте как обычный контекст задачи. Его существующий объём — единственное исключение.
- Пишите кратко и конкретно.
- У каждой темы должен быть один источник истины; используйте ссылки вместо дублирования.
- Описывайте текущие решения, а не гипотетическую корпоративную архитектуру.
- Явно разделяйте MVP, полировку после MVP и дополнительные возможности.
- Неизвестные решения фиксируйте явно, не придумывайте их.
- Создавайте документ только при наличии понятной цели.
- Будущие агенты должны читать только документацию, относящуюся к их задаче.
- Не рефакторите приложение, если это прямо не требуется задачей.
- Структуру, этапы и жизненный цикл документации определяет `docs/DOCUMENTATION.md`.

## Маршруты чтения

- Задача по бэкенду: этот файл + `docs/BACKEND.md` + нужный раздел `docs/MVP.md`.
- Задача по фронтенду: этот файл + `docs/FRONTEND.md` + `docs/DESIGN.md`.
- Общий контракт или системный поток: этот файл + `docs/ARCHITECTURE.md`.
- GitHub, realtime или n8n: этот файл + `docs/INTEGRATIONS.md`.
- Решение по продукту или границам: `docs/PRODUCT.md` + `docs/MVP.md`.
- Планирование и смена приоритетов: `docs/MVP.md` + `docs/IMPLEMENTATION_PLAN.md`.
- Демонстрация или полировка: `docs/DEMO.md` + `docs/DESIGN.md`.
- Создание или завершение этапа: `docs/DOCUMENTATION.md` + README текущего этапа.
