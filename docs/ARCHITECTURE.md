# Архитектура

## Существующий стек

- Бэкенд: Java 21, Spring Boot 4.1.1, Maven, Spring MVC, JPA, Validation, Liquibase, зависимость WebSocket.
- Фронтенд: Vue 3, TypeScript, Quasar 2, Composition API, Axios, Vue Router и Pinia.
- База данных: PostgreSQL 17 через Docker Compose.
- Реализовано: доменное хранение, CRUD Квестов и Raid, сервис прогресса, атомарный reset, STOMP-канал и живой Vue-интерфейс.

## Границы

```text
GitHub или демо-триггер
        |
интеграционный адаптер/контроллер
        |
сервис Spring -> JPA-репозитории -> PostgreSQL
        |
ответ API и необязательное realtime-событие
        |
интерфейс Vue/Quasar
```

- Spring Boot владеет состоянием Квестов, достижений и правилами XP, уровней, наград и рейда.
- PostgreSQL — долговременный источник истины.
- Vue отвечает за представление и последовательность анимаций, но не рассчитывает прогресс.
- GitHub/n8n переводят внешние события во внутренние команды и не рассчитывают награды.

## Основной поток данных

Чтение Dashboard выполняется через `GET /api/demo/state`, а управление Raid — через `/api/raids`. Команда завершения входит в одну транзакцию сервиса и возвращает `ProgressionResponse`, представленный на фронтенде типом `ProgressionResult`. Тот же JSON отправляется подключённым STOMP-клиентам.

`DemoState` содержит список игроков и общую доску. Выбор профиля существует только во frontend и не участвует в авторизации или начислении XP: прогресс всегда получает `Quest.assignee`. Состояние `coding` рассчитывается по `IN_PROGRESS` Квестам конкретного игрока.

Повторное завершение не должно повторно начислять прогресс. Это гарантирует сервис и модель хранения, а не только интерфейс.

Достижения принадлежат игроку и хранятся в `player_achievement`. Их фиксированный каталог находится в backend-коде. После применённого завершения Квеста `AchievementService` обновляет нужные счётчики внутри той же транзакции, а новые открытия входят в `ProgressionResponse`. Начальные XP и завершённые seed-Квесты не создают достижений задним числом.

Raid имеет lifecycle `DRAFT → ACTIVE → COMPLETED` и `DRAFT/ACTIVE → CANCELLED`. В БД и сервисе разрешён максимум один `ACTIVE`. Только он получает урон; отсутствие активного Raid не мешает завершению Квеста и начислению XP.

## Realtime

STOMP доступен через `/ws`, исходящие результаты — через `/topic/progression`. Используется встроенный простой broker, внешний брокер сообщений не нужен. Запасной вариант MVP — обновить инициирующий клиент из REST-ответа и перечитать состояние после ошибки соединения.

## Граница внешних интеграций

Детерминированный демо-endpoint и будущий GitHub webhook вызывают один сервис приложения. См. [INTEGRATIONS.md](INTEGRATIONS.md).

## Общие контракты

Контракт демо зафиксирован в [stages/00-contracts/README.md](stages/00-contracts/README.md). Его основные решения:

- статусы Квеста: `TODO`, `IN_PROGRESS`, `DONE`;
- поля read-модели для Dashboard и Квестов;
- идентификатор команды завершения и payload `ProgressionResult`;
- постоянные состояния персонажа: `idle`, `coding`; реакции события: `happy`, `level-up`;
- ошибки для отсутствующего и уже завершённого Квеста.

DTO контрактов и Liquibase changelog — конфликтные файлы; у них должен быть один активный владелец.

## Осознанно исключено

Для MVP не проектируются аутентификация, распределённые события, универсальный rules engine, отдельный интеграционный сервис и корпоративная многослойность. Возвращаться к ним только при конкретной потребности работающего демо.
