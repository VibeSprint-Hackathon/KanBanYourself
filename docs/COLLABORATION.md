# Правила совместной работы

## Рабочая модель

Три разработчика работают в узких областях, возможно с AI-агентами. У каждой задачи обычно одна цель, один владелец, одна ветка/worktree и ограниченный набор файлов.

Текущее владение:

- Тимофей закрыл поток A и временную backend-часть C: reset и realtime.
- Андрей, поток B — Vue Dashboard, frontend API, состояния запросов и анимация; ближайшая общая точка — I1.
- Никита — основной владелец потока C и сможет продолжить внешние интеграции после возвращения.

Менять владение можно по опыту и доступности, но у общей области должен быть один активный владелец.

## Ветки и worktree

- Начинать от последней демонстрируемой основной ветки.
- Одна короткоживущая ветка/worktree на задачу.
- Сохранять изменения узкими; агенты не создают коммиты без явного запроса.
- Перед передачей обновляться согласно выбранной командой Git-политике.
- Не смешивать экспериментальные дополнения с MVP-ветками.

Merge/rebase-политика — решение команды; последовательность важнее конкретного выбора.

## Общие и конфликтные файлы

Согласовывать изменения заранее:

- Liquibase master, схема и seed-данные.
- API DTO и контракт события прогресса.
- сервис прогресса и общие доменные сущности.
- router, глобальные стили, layout, API-типы и точка входа Pinia.
- Maven/package/configuration файлы.

После фиксации контрактов предпочитать добавление feature-файлов. Не поручать агентам параллельно создавать разные абстракции одного контракта.

## Сначала контракты

Этап 0 создаёт один согласованный пример для:

- ответа состояния демо;
- команды завершения Квеста;
- результата/события прогресса;
- enum статуса и состояния персонажа;
- поведения повторного завершения.

Фронтенд может работать с fixture, точно соответствующим контракту. Бэкенд владеет расчётами. Изменения контракта объявляются всем владельцам до продолжения.

## Ритм интеграции

- Объединять стабильную работу каждые 60–90 минут.
- На каждой точке загружать состояние, запускать завершение и проверять весь сценарий.
- Основная ветка остаётся последним разумно демонстрируемым состоянием.
- До дополнительных функций зафиксировать стабильный MVP и запасной запуск.

Контрольные точки:

1. Согласованы контракты и демо-данные.
2. Транзакция бэкенда и статический UI работают отдельно.
3. Интегрирован REST-сценарий.
4. Интегрированы анимация/realtime-полировка.
5. Проверены финальная репетиция и запасной путь.

## Правила для AI-агентов

- Указывать цель, разрешённые области, запреты, входные контракты и проверку.
- Агент читает только документы по маршруту из корневого `AGENTS.md`.
- Сначала изучать, затем редактировать; сохранять чужие изменения.
- Не разрешать агентам независимо менять общие DTO или схему.
- Использовать агентов для ограниченной многофайловой работы, интеграций, тестов и review, а не мелких правок.
- О необходимости изменить общий файл вне области агент сообщает заранее.
- Один человек проверяет сгенерированные контракты и миграции до интеграции.

## Передача результата

- Перечислить изменения и затронутые файлы.
- Указать проверки и ограничения.
- Отдельно отметить изменения контрактов/схемы.
- Назвать следующую задачу, не начиная её скрытно.
