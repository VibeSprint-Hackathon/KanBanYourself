# План реализации

План нацелен на надёжный вертикальный сценарий за пять часов, затем — на одно запоминающееся улучшение. Временные рамки нужны для координации, а не являются обещанием.

Правила создания и завершения документации каждого этапа описаны в [DOCUMENTATION.md](DOCUMENTATION.md).

Распределение потоков: A — Тимофей, B — Андрей, C — Никита. Буквы обозначают технические области, а не иерархию.

## Этап 0 — контракты и координация (0:00–0:30)

### 0.1 Зафиксировать контракт демо — выполнено

- Цель: согласовать read-модель, команду завершения, `ProgressionResult`, enum, порог уровня и правило урона.
- Согласование: совместное; отдельного владельца решений нет, файл редактирует один человек за раз.
- Зависимости: нет.
- Результат: [контракт этапа 00](stages/00-contracts/README.md); затем по нему создаются DTO бэкенда и API-типы фронтенда.
- Проверка: JSON-примеры покрывают загрузку, reset, 920 XP + 180 XP, уровень, награду, победу и повтор команды.
- Исполнение: ручное решение команды; AI может создать типы после утверждения.

### 0.2 Зафиксировать владение и запасной путь — выполнено

- Цель: разделить области A/B/C, определить конфликтные файлы и выбрать способ обновления UI.
- Согласование: совместное; роли задают технические границы, а не старшинство.
- Зависимости: 0.1.
- Результат: границы и порядок интеграции зафиксированы в [README этапа 00](stages/00-contracts/README.md).
- Проверка: области не пересекаются без согласования; REST-ответ и демо-триггер являются обязательным запасным путём.
- Исполнение: вручную, поскольку решение зависит от доступности людей и риска конфликтов.

Контрольная точка пройдена: контракт согласован; за схему и поток A отвечает Тимофей, за B — Андрей, за C — Никита.

## Первые ~5 часов — демонстрируемый MVP

### Поток A — вертикаль бэкенда (0:30–2:30)

#### A1. Доменная схема и демо-данные

- Цель: заменить или дополнить временную схему минимальным хранением Игрока, Квеста и Рейда с подготовленным состоянием.
- Владелец: Разработчик A, бэкенд/хранение.
- Зависимости: 0.1.
- Вероятные файлы: `backend/src/main/resources/db/changelog/**`, доменные сущности/репозитории.
- Проверка: Liquibase запускается на пустой БД, JPA validation проходит, seed совпадает с [DEMO.md](DEMO.md).
- Исполнение: хорошая задача AI после утверждения схемы; migration review выполняется вручную.
- Спецификация к реализации: [BACKEND_A1.md](stages/01-mvp/BACKEND_A1.md).

#### A2. Атомарный сервис прогресса

- Цель: завершить Квест, начислить XP, рассчитать уровень/награду и нанести урон ровно один раз в одной транзакции.
- Владелец: Разработчик A, ядро бэкенда.
- Зависимости: A1.
- Вероятные файлы: сервисы Квеста/игрока/рейда и тесты.
- Проверка: тесты обычного завершения, уровня/награды/победы и повторной команды.
- Исполнение: хорошая узкая задача AI с явными пакетами и правилами.
- Спецификация к реализации: раздел A2 в [README этапа 01](stages/01-mvp/README.md).

#### A3. API чтения и демо-команды

- Цель: открыть согласованное чтение состояния и детерминированную команду завершения через DTO.
- Владелец: A; C владеет только границей адаптера после фиксации сервиса.
- Зависимости: A2 и контракт 0.1.
- Вероятные файлы: контроллеры/DTO бэкенда, необязательный demo adapter.
- Проверка: HTTP возвращает согласованный payload, refresh показывает сохранённый результат.
- Исполнение: хорошая задача AI; совместимость payload проверяется вручную.

### Поток B — сцена фронтенда (0:30–2:30, параллельно A)

#### B1. Типизированный API и fixture

- Цель: описать согласованные DTO и дать UI fixture до готовности A3.
- Владелец: Разработчик B, фронтенд.
- Зависимости: 0.1.
- Вероятные файлы: `frontend/src/api/**`, файл DTO-типов, временный fixture.
- Проверка: строгий typecheck; fixture точно соответствует JSON-примеру.
- Исполнение: хорошая задача AI; fixture удалить/обойти при интеграции API.

#### B2. Компоновка Dashboard

- Цель: показать игрока, активный Квест, персонажа, XP, следующую награду и босса на одной странице.
- Владелец: Разработчик B.
- Зависимости: B1 и доступный визуальный референс/ассеты.
- Вероятные файлы: `frontend/src/pages/IndexPage.vue`, `src/components/dashboard/**`, scoped styles.
- Проверка: визуальная проверка в разрешении презентации; все факты видны без навигации.
- Исполнение: AI подходит для реализации; визуальное решение и сравнение скриншотов — вручную.

#### B3. Квесты и состояния прогресса

- Цель: показать минимальные колонки и последовательность Квест -> XP -> персонаж -> награда -> босс.
- Владелец: Разработчик B.
- Зависимости: B2 и контракт 0.1.
- Вероятные файлы: `src/components/quests/**`, `src/components/progression/**`, ассеты.
- Проверка: последовательность запускается из fixture; без анимации остаётся правильное финальное состояние.
- Исполнение: AI создаёт компоненты; timing и полировка настраиваются вручную.

### Поток C — доставка событий и надёжное демо (0:30–2:30, параллельно)

Разработчик C соединяет готовую бизнес-логику с внешними событиями и интерфейсом. Он не рассчитывает XP, уровни или урон: этим владеет сервис из A2.

Простой целевой поток:

`GitHub или демо-кнопка -> команда завершения Квеста -> сервис A2 -> результат для UI`

#### C1. Выбрать способ обновления интерфейса

- Цель: понять, как UI сразу узнает о завершении Квеста и новом прогрессе.
- Владелец: Разработчик C; изменение фронтенда согласуется с B.
- Зависимости: контракт 0.1 и команда сервиса A2.
- Действия: сначала проверить обычный REST-ответ, затем потратить не более 30 минут на простой WebSocket.
- Решение: если WebSocket работает просто и стабильно — оставить; иначе обновлять UI из REST-ответа.
- Вероятные файлы: backend `integration`/`realtime`, необязательный frontend realtime-клиент.
- Проверка: одно завершение даёт одно обновление; повторное событие не дублирует награду.
- Результат: команда явно знает основной и запасной способы обновления UI.

#### C2. Сделать надёжный демо-триггер

- Цель: запускать полный сценарий без зависимости от GitHub, сети или реального merge PR.
- Владелец: Разработчик C совместно с A.
- Зависимости: сервис A2; форму endpoint можно согласовать заранее.
- Действия: добавить команду `подготовить демо` и команду `завершить демо-Квест`.
- Важно: триггер вызывает сервис A2 и не изменяет XP, Квест или босса напрямую.
- Вероятные файлы: demo controller/service и, при необходимости, небольшая кнопка в UI.
- Проверка: подготовить -> завершить -> обновить страницу -> повторить завершение -> снова подготовить.
- Результат: сценарий можно многократно репетировать без ручного изменения базы данных.

#### Что не входит в поток C на этом этапе

- Полная GitHub-интеграция, GitHub App и поддержка множества событий.
- Собственная логика XP, уровней, косметики или рейда.
- Сложное переподключение WebSocket и отдельная событийная инфраструктура.

Реальный GitHub webhook начинать только после работающего REST-сценария и надёжного демо-триггера.

### Интеграция (2:30–4:00)

#### I1. Заменить fixture живым бэкендом

- Цель: подключить UI B к endpoints A и выбранному C способу обновления.
- Владелец: B меняет фронтенд; A исправляет контракт бэкенда; C — события.
- Зависимости: A3, B3 и решение C1.
- Вероятные файлы: frontend API/composable/store и только необходимые backend DTO.
- Проверка: пустая БД -> запуск -> загрузка -> завершение -> анимация -> refresh без ручной правки данных.
- Исполнение: парная/ручная интеграция; AI только для изолированных диагностированных дефектов.

#### I2. Проверка надёжности полного сценария

- Цель: исключить повторные награды, устаревший UI, ошибки ассетов и неясные ошибки.
- Владелец: вся команда, по одному владельцу на дефект.
- Зависимости: I1.
- Вероятные файлы: только относящиеся к воспроизведённым дефектам.
- Проверка: чек-лист [DEMO.md](DEMO.md) проходит три раза.
- Исполнение: тестирование ведётся вручную; AI полезен для узких исправлений и тестов.

### Полировка и фиксация MVP (4:00–5:00)

#### P1. Полировка презентации

- Цель: улучшить один момент демо без расширения функциональности.
- Владелец: B ведёт визуальную часть; A/C защищают надёжность.
- Зависимости: I2.
- Вероятные файлы: scoped styles, timing, локальные ассеты, микротекст.
- Проверка: скриншоты, разрешение презентации, финальное состояние с reduced motion.
- Исполнение: преимущественно вручную с ограниченными AI-правками.

#### P2. Зафиксировать запасной вариант

- Цель: сохранить последнее демонстрируемое состояние и инструкцию ведущему.
- Владелец: вся команда; один человек запускает без контекста реализации.
- Зависимости: P1.
- Вероятные файлы: без новой продуктовой области; обновить демо-документ только при расхождении.
- Проверка: холодный запуск и полный сценарий без внешних сервисов.
- Исполнение: вручную.

Выход MVP: выполнены все условия [MVP.md](MVP.md) и детерминированный путь [DEMO.md](DEMO.md).

## После MVP — порядок выбора

1. Надёжность и визуальная полировка: исправить сбои репетиции, настроить персонажа и loading/error состояния.
2. Реальный GitHub merged-PR: только при предсказуемом deployment/webhook; демо-триггер сохраняется.
3. Выбрать одну возможность по оставшемуся времени и ассетам:
   - развитие персонажа, если готова графика;
   - браузерный компаньон, если стабилен realtime;
   - экспорт достижения, если быстро получается качественная композиция;
   - AI-оценка сложности/XP, только если внешняя задержка даёт заметную ценность.
4. Вовремя остановить разработку ради финальной интеграции, настройки презентации и репетиций.

Не считать все дополнительные идеи обязательными. Одна завершённая возможность лучше нескольких частичных.
