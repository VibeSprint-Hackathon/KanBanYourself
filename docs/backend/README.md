# Бэкенд

## Текущее состояние

Бэкенд — приложение Spring Boot с PostgreSQL, Liquibase, JPA, Validation и WebSocket/STOMP. A1 добавил хранение, A2 — атомарный прогресс, A3 — REST API, C1/C2 — исходящий realtime и атомарный reset.

## Локальная среда

- Использовать JDK 21; `pom.xml` остаётся источником версии Java.
- PostgreSQL 17 запускается через `docker compose up -d postgres`.
- Контейнер слушает `5432`, а хост по умолчанию — `55432`, чтобы не конфликтовать с установленным PostgreSQL.
- Порт хоста можно изменить через `POSTGRES_PORT`; полный JDBC URL — через `SPRING_DATASOURCE_URL`.

## Ответственность

- Отдавать текущее состояние игрока, доски Квестов и рейда.
- Принимать идемпотентные команды завершения Квеста.
- Владеть переходами Квестов, XP, уровнями, наградами, состоянием персонажа и уроном рейду.
- Атомарно сохранять состояние и при наличии realtime публиковать результат прогресса.
- Принимать нормализованную активность от демонстрационного и GitHub-адаптеров.

## Ожидаемые доменные области

Использовать минимальные пакеты внутри `com.vibesprint.backend`:

- `quest`: сущность, статус, репозиторий, сервис, DTO и контроллер Квеста.
- `player`: сущность игрока/прогресса и расчёт в сервисе.
- `raid`: сущность рейда и изменение урона.
- `progression`: единая транзакция, правила уровней/наград и внутренний результат завершения.
- `api`: агрегированное чтение, REST DTO, mapper, controller и единый формат HTTP-ошибок.
- `integration`: демо-триггер и будущие входные адаптеры GitHub.
- `realtime`: необязательная конфигурация исходящих событий прогресса.

Для MVP не разделять их на дополнительные модули.

## Модель хранения MVP

- `Player`: id, имя и общий XP.
- `Quest`: id, название, статус, награда XP, исполнитель и nullable внешняя ссылка.
- `Raid`: id, название, максимальный и текущий HP.

Уровень, следующий порог, титул, косметика, состояние персонажа и статус рейда вычисляются, а не хранятся. Точная схема и seed зафиксированы в [BACKEND_A1.md](../stages/01-mvp/BACKEND_A1.md).

## Граница DTO и API

Контроллеры принимают/возвращают DTO и сразу делегируют сервисам. JPA-сущности не выходят наружу.

Описание доступных endpoint, JSON-полей и ошибок: [API.md](API.md).

Контракты зафиксированы в [README этапа 00](../stages/00-contracts/README.md). Реализованы:

- `GET /api/demo/state` для состояния Dashboard и доски;
- `POST /api/demo/quests/{questId}/complete` для завершения Квеста;
- `ProgressionResponse` с обновлёнными Квестом, игроком, рейдом и результатом награды.

`POST /api/demo/reset` восстанавливает исходный seed. STOMP endpoint `/ws` публикует применённый результат в `/topic/progression`. Точные контракты описаны в [API.md](API.md), а код и тесты являются источником истины реализации.

## Хранение и прогресс

- PostgreSQL является источником истины; использовать JPA-репозитории.
- Завершать Квест и применять весь прогресс в одной транзакции.
- Повторное завершение не начисляет XP и урон заново.
- Бэкенд рассчитывает уровни/награды; фронтенд только показывает результат.
- Начальная формула должна быть простой и закреплённой тестами, а не дублированной в документах.

## Liquibase

- Все изменения схемы и seed-данных добавляются в `backend/src/main/resources/db/changelog/changes/`.
- Каждый changeset подключается из `db.changelog-master.yaml`.
- Не использовать создание схемы через Hibernate; `ddl-auto: validate` оставлен намеренно.
- Удалить временную таблицу `example_item` новым changeset `002`, не переписывая `001`.
- Добавлять только детерминированные данные, необходимые для [DEMO.md](../DEMO.md).

## Тестирование

- Unit-тесты порогов прогресса и повторного завершения.
- Один сервисный/интеграционный тест атомарного изменения Квеста, Игрока и Рейда.
- Сохранить существующий smoke-тест загрузки контекста.
- Для узкой задачи запускать минимальный подходящий набор Maven-тестов.

## Конфликтные области

- Liquibase master, доменная схема и seed-данные.
- Общие DTO и результат прогресса.
- Сервис прогресса/транзакция.
- Realtime-конфигурация и payload события.

В каждый момент у них должен быть один владелец. Адаптеры вызывают сервис прогресса и не повторяют его правила.
