# A1 — схема, сущности и репозитории

Владелец: Тимофей  
Статус: `DONE`
Область реализации: `backend/`

## Цель

Создать минимальную модель хранения, достаточную для следующего шага A2. После A1 приложение умеет поднять схему и прочитать подготовленное состояние, но ещё не завершает Квесты.

## Принципы модели

- Хранить только факты, которые меняются и должны пережить перезапуск.
- Вычислять производные значения, чтобы они не расходились с XP или HP.
- Не создавать универсальную игровую модель, event store или аудит событий.
- Сохранять однонаправленные связи и минимальный JPA mapping.
- Использовать зафиксированные числовые id; создание новых объектов через API пока отсутствует.

## Таблица `player`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | primary key, назначается seed |
| `name` | `VARCHAR(100)` | not null, непустое значение |
| `total_xp` | `INTEGER` | not null, `>= 0` |

Не хранить `level`, `nextLevelXp`, `title`, `cosmeticKey` и `characterState`.

Они вычисляются позже в read-модели:

- уровень, титул и косметика — из `total_xp`;
- следующий порог — из таблицы уровней в коде A2;
- состояние `coding` — при наличии Квеста `IN_PROGRESS`, иначе `idle`.

## Таблица `quest`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | primary key, назначается seed |
| `title` | `VARCHAR(255)` | not null, непустое значение |
| `status` | `VARCHAR(32)` | `TODO`, `IN_PROGRESS` или `DONE` |
| `xp_reward` | `INTEGER` | not null, `> 0` |
| `assignee_id` | `BIGINT` | not null, FK на `player.id` |
| `external_reference` | `VARCHAR(500)` | nullable URL или внешний идентификатор |

`externalReference` в REST — строка или `null`. Для MVP не раскладывать GitHub-ссылку на provider/repository/number.

Связь с игроком: `@ManyToOne(fetch = LAZY, optional = false)`. Обратная коллекция Квестов в `Player` не нужна. Cascade delete не использовать.

## Таблица `raid`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | primary key, назначается seed |
| `name` | `VARCHAR(255)` | not null, непустое значение |
| `max_hp` | `INTEGER` | not null, `> 0` |
| `current_hp` | `INTEGER` | not null, от `0` до `max_hp` |

Не хранить `status`: `ACTIVE`, если `current_hp > 0`, иначе `DEFEATED`.

В MVP существует один рейд. Таблица команды и связь Quest -> Raid не нужны. `ProgressionService` A2 получает единственный рейд через репозиторий и возвращает `DEMO_STATE_NOT_READY`, если его нет.

## Liquibase

Создать `backend/src/main/resources/db/changelog/changes/002-mvp-domain.yaml` и подключить его после `001`.

Changeset выполняет по порядку:

1. Удаляет временную таблицу `example_item`.
2. Создаёт `player`.
3. Создаёт `quest` и FK на игрока.
4. Создаёт `raid`.
5. Добавляет ограничения допустимых значений.
6. Добавляет подготовленные записи.

Не редактировать `001-initial-schema.yaml`: новая миграция должна работать и на уже созданной, и на чистой БД.

```text
│   ├── Player.java

│   ├── Quest.java
│   ├── QuestStatus.java

```

Не создавать в A1 контроллеры, DTO, сервисы, mapper-классы или базовые абстракции сущностей.

## JPA mapping

- Имена таблиц и колонок указывать явно.
- Enum хранить как строку через `EnumType.STRING`.
- Для сущностей нужен защищённый конструктор без аргументов.
- Не использовать `EAGER`, двусторонние связи и каскадное удаление.
- Не добавлять timestamps: контракт и MVP их не используют.
- Не добавлять `@Version`: повтор одного Квеста защищает блокирующий запрос.

## Репозитории

- `PlayerRepository`: обычный `JpaRepository<Player, Long>`.
- `QuestRepository`: чтение всех Квестов по `id` и отдельный `findByIdForUpdate` с `PESSIMISTIC_WRITE` для A2.
- `RaidRepository`: детерминированное получение единственного рейда по наименьшему `id`.

Блокировка нужна только в транзакции A2. Она защищает от двух одновременных завершений одного Квеста; второй запрос после ожидания увидит `DONE`.

## Ограничения и ошибки

База должна запрещать отрицательные XP/HP, неизвестный статус, отсутствующего assignee и `current_hp > max_hp`. Доменные ошибки API появятся в A3; A1 не добавляет глобальный exception handler.

## Проверка A1

1. Запустить существующий PostgreSQL через Docker Compose.
2. Запустить Maven-тесты или приложение на чистой базе.
3. Убедиться, что применились `001` и `002`, а `example_item` удалена.
4. Проверить, что Hibernate `ddl-auto: validate` не сообщает расхождений.
5. Repository test читает игрока 1, Квесты 101–103 и рейд 201.
6. Блокирующий запрос Квеста вызывается внутри тестовой транзакции.
7. Повторный запуск миграций не изменяет данные и не падает.

Минимальные команды проверки из каталога проекта:

```text
docker compose up -d postgres
backend\mvnw.cmd -f backend\pom.xml test
```

Не добавлять H2, Testcontainers или другие зависимости только ради A1.

## Риски и границы

- Контракт использует демонстрационные id; генерация новых id откладывается до появления create API.
- Singleton raid — осознанное ограничение MVP.
- Reset из потока C позже восстанавливает эти же значения через сервис, а не перезапускает Liquibase.
- Если точный Liquibase-синтаксис ограничения несовместим с текущей версией, использовать минимальный PostgreSQL SQL внутри changeset, не ослабляя правило.

## Состояние реализации

Схема, seed-данные, JPA-сущности, репозитории и `MvpPersistenceTests` реализованы. Проверка на чистом PostgreSQL 17 подтвердила применение `001` и `002`, удаление `example_item`, Hibernate validation, чтение seed и блокирующий запрос.

Повторный запуск Liquibase не применил changeset повторно. Все 3 backend-теста завершились без ошибок. A1 закрыт, следующим шагом можно планировать A2.

Любое дальнейшее изменение таблиц, REST-полей или seed-сценария сначала отражается здесь и согласуется с потоками B/C.
