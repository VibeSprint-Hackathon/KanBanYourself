# Этап 01 — MVP

Статус: `ACTIVE`  
Текущий подэтап: `A1 — READY_TO_IMPLEMENT`

## Результат этапа

Работающий вертикальный сценарий: загрузить подготовленное состояние, завершить Квест один раз, получить прогресс игрока и рейда, обновить UI без перезагрузки.

## Владение

| Поток | Участник | Область |

| A | Тимофей | Схема, доменные сущности, репозитории, прогресс и REST DTO |

| C | Никита | Демо-адаптер, доставка событий и необязательный realtime |

## Текущий подэтап A1

Цель: подготовить устойчивую базу для A2 — схему, демонстрационные данные, JPA-сущности и репозитории без бизнес-логики завершения.

Полная спецификация: [BACKEND_A1.md](BACKEND_A1.md).

### Входит

- Liquibase changeset `002-mvp-domain.yaml`.
- Таблицы `player`, `quest`, `raid` и ограничения.
- Удаление временной таблицы `example_item` новым changeset.
- Детерминированные seed-данные.
- JPA-сущности, enum и репозитории.
- Repository smoke test или эквивалентная проверка чтения seed.

### Не входит

- `ProgressionService`, расчёт завершения и транзакция A2.
- REST-контроллеры и DTO A3.
- Reset/complete адаптер потока C.
- WebSocket, GitHub и изменения фронтенда.
- Аутентификация и новые зависимости.

## Точки интеграции

- B продолжает использовать fixture из зафиксированного контракта и не зависит от схемы БД.
- C не обращается к репозиториям A напрямую; он ждёт публичный сервис A2.
- Изменения `CONTRACTS.md` требуют совместного решения команды.
- `db.changelog-master.yaml` и доменные сущности во время A1 изменяет только Тимофей.

## Контрольные точки

1. A1: чистая БД мигрирует, seed читается через JPA.
2. A2: завершение Квеста атомарно и идемпотентно.
3. A3: REST точно соответствует `CONTRACTS.md`.
4. I1: UI работает с живым REST вместо fixture.
5. I2: reset -> complete -> повтор -> reset проходит три раза.

## Критерий завершения A1

- Схема создаётся с нуля через Liquibase.
- Hibernate `validate` принимает схему.
- `example_item` отсутствует.
- Seed содержит игрока, три Квеста и один рейд.
- Репозитории возвращают ожидаемые записи и блокирующий запрос Квеста.
- Health endpoint продолжает работать.
- Не добавлены зависимости и поведение API не изменено.

## Передача в A2

После A1 Тимофей реализует одну транзакцию прогресса поверх готовых репозиториев. Фактические имена созданных Java-файлов и выполненные проверки записываются сюда при закрытии A1.
