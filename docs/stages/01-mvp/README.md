## Подэтап A2 — атомарный сервис прогресса

Цель: одной транзакцией завершить Квест, начислить XP, вычислить прогресс и награду, нанести урон рейду и безопасно обработать повтор команды.

Владелец: Тимофей. Основная область: `backend/src/main/java/com/vibesprint/backend/progression/`, доменные сущности и блокирующие запросы репозиториев.

### Публичная граница сервиса

`ProgressionService.completeQuest(command)` принимает внутреннюю команду:

- положительный `questId`;
- непустой `eventId`;
- `source`: `DEMO` или `GITHUB`.

Сервис возвращает неизменяемый `ProgressionResult` с семантикой из [CONTRACTS.md](../00-contracts/CONTRACTS.md): `applied`, причина повтора, начисления, повышение уровня, награда, реакция, признак победы и полные снимки Квеста, игрока и рейда.

Это внутренняя Java-модель, а не REST DTO. A3 отвечает за HTTP validation, JSON-имена и коды статусов. Поток C вызывает только эту границу и не использует репозитории.

### Алгоритм транзакции

Публичный метод помечается `@Transactional` и выполняет шаги в фиксированном порядке:

1. Проверить команду без изменения состояния.
2. Получить Квест через `findByIdForUpdate`; при отсутствии — `QUEST_NOT_FOUND`.
3. Заблокировать назначенного игрока.
4. Заблокировать единственный рейд по наименьшему id.
5. До мутаций убедиться, что подготовленное состояние полно.
6. Если Квест уже `DONE`, вернуть текущие снимки и нулевые начисления.
7. Иначе перевести Квест в `DONE`, добавить его XP игроку и нанести такой же урон рейду.
8. Рассчитать результат до/после и завершить транзакцию.

Блокировки игрока и рейда нужны для одновременного завершения разных Квестов. Все будущие операции, меняющие те же записи, должны соблюдать совместимый порядок блокировок.

### Правила расчёта

- `ProgressionRules` реализует фиксированные пороги и демонстрационные значения из [контракта этапа 0](../00-contracts/README.md); отдельная конфигурация в БД не нужна.
- Уровень определяется по общему XP; остаток после повышения сохраняется.
- Уровень рассчитывается до и после начисления, а награда выдаётся только при первом пересечении её порога.
- `levelUp=true`, если новый уровень выше прежнего, даже при пересечении нескольких порогов.
- Урон равен начисленному XP; HP рейда ограничивается нулём.
- При успехе реакция `level-up` имеет приоритет, иначе используется `happy`.
- `bossDefeated=true`, когда итоговый HP равен нулю, в том числе в ответе на повтор.
- Для `DONE`: `applied=false`, причина `ALREADY_COMPLETED`, начисления равны нулю, реакция и награда отсутствуют.

`eventId` возвращается вызывающему коду, но в A2 не хранится. Идемпотентность MVP определяется состоянием Квеста; event store и таблица обработанных событий не нужны.

### Изменения модели A1

- `Quest`: доменный метод перехода в `DONE`, без публичного setter.
- `Player`: метод безопасного добавления положительного XP.
- `Raid`: метод нанесения положительного урона с ограничением HP нулём.
- `PlayerRepository`: блокирующее чтение игрока по id.
- `RaidRepository`: блокирующее получение рейда с наименьшим id.
- `QuestRepository`: использовать готовый `findByIdForUpdate`.

Изменения схемы и новый Liquibase changeset не требуются.

### Ошибки и откат

- Некорректная команда становится доменной ошибкой A2; A3 позже преобразует её в `400 INVALID_REQUEST`.
- Отсутствующий Квест — доменная ошибка для `404 QUEST_NOT_FOUND`.
- Отсутствующий игрок или рейд — ошибка для `409 DEMO_STATE_NOT_READY`.
- Любая ошибка после начала транзакции откатывает все изменения.
- Внутренние детали и исключения JPA не становятся частью публичного ответа.

## Точки интеграции

- B продолжает работать по зафиксированному fixture и не зависит от Java-модели A2.
- C после A2 получает `ProgressionService`; прямое изменение сущностей ему запрещено.
- A3 отображает внутренний результат A2 в точный REST-контракт без повторного расчёта.
- Изменение JSON, seed или формулы требует совместного решения команды.

## Контрольные точки

1. A1: чистая БД мигрирует, seed читается через JPA.
2. A2: завершение Квеста атомарно и идемпотентно.
3. A3: REST точно соответствует `CONTRACTS.md`.
4. I1: UI работает с живым REST вместо fixture.
5. I2: reset -> complete -> повтор -> reset проходит три раза.

## Критерий завершения A2

- Одна транзакция владеет всеми изменениями Квеста, игрока и рейда.
- Обычное, повторное и параллельное завершение соответствуют контракту.
- Результат содержит всё необходимое A3 и потоку C без доступа к сущностям.
- Ошибки не оставляют частично обновлённое состояние.
- Схема, REST API и зависимости не изменены.
