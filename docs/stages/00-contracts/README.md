# Этап 00 — контракты

Статус этапа: `DONE`  
Подэтап 0.1: `FROZEN`  
Подэтап 0.2: `FROZEN`  
Согласование: совместное; отдельного владельца решений нет, файл редактирует один человек за раз.

## Результат 0.1

Зафиксирован минимальный контракт демонстрации. Бэкенд, фронтенд и интеграционный адаптер могут реализовывать свои части независимо, используя одинаковые имена и правила.

## Область

- Входит: агрегированное состояние демо, завершение Квеста, сброс, прогресс, ошибки и повтор команды.
- Не входит: таблицы БД, Java/TypeScript-классы, WebSocket transport, GitHub webhook и аутентификация.

## Демонстрационный сценарий

- Игрок `Andrei`: уровень 4, 920 общего XP, следующий уровень на 1000 XP.
- Квест `Fix payment validation`: статус `IN_PROGRESS`, награда 180 XP.
- Босс `Merge Conflict Hydra`: 180 из 1000 HP.
- Завершение Квеста даёт 180 XP и 180 урона.
- Итог: 1100 XP, уровень 5, косметика `rare-hoodie`, босс побеждён.

## Общие значения

Статус Квеста: `TODO | IN_PROGRESS | DONE`.  
Статус рейда: `ACTIVE | DEFEATED`.  
Постоянное состояние персонажа: `idle | coding`.  
Временная реакция результата: `happy | level-up`.  
Источник события: `DEMO | GITHUB`.

Идентификаторы доменных объектов — положительные числа. Дата/время, если добавляется, передаётся в UTC ISO 8601.

## REST-контракт

Точные endpoints, запросы и ответы вынесены в [CONTRACTS.md](CONTRACTS.md). Это единственный источник истины для JSON этапа 0.1.

## Правила прогресса

- Уровень определяется по общему XP: L1=0, L2=200, L3=400, L4=600, L5=1000, L6=1500.
- Лишний XP сохраняется: 920 + 180 = 1100, а не 100 после повышения уровня.
- Урон рейду равен фактически начисленному XP.
- HP не может стать меньше нуля.
- `level-up` имеет приоритет над `happy`; иначе успешное завершение возвращает `happy`.
- `characterState` после завершения — `idle`; реакция является временным UI-событием.
- Завершение `TODO` или `IN_PROGRESS` допустимо; оба переходят в `DONE`.
- Квест, XP, уровень, награда и рейд обновляются в одной транзакции.

## Ошибки

- `400 INVALID_REQUEST`: пустой `eventId`, неизвестный `source` или некорректный id.
- `404 QUEST_NOT_FOUND`: Квест не существует.
- `409 DEMO_STATE_NOT_READY`: подготовленные игрок или рейд отсутствуют.
- `500 INTERNAL_ERROR`: неожиданный сбой; детали реализации наружу не возвращаются.

## Проверка контракта

- Reset возвращает исходные 920 XP, Квест `IN_PROGRESS` и 180 HP.
- Первый complete возвращает `applied=true`, 1100 XP, уровень 5 и 0 HP.
- Второй complete возвращает `applied=false`, нулевые приращения и неизменное состояние.
- Повторный reset позволяет заново выполнить тот же сценарий.
- Java DTO и TypeScript-типы должны представлять эти ответы без переименования полей.

## Результат 0.2

Работа разделена на три технические зоны. Буквы A/B/C обозначают области, а не старшинство или право принимать решения.

- Поток A — Тимофей.
- Поток B — Андрей.
- Поток C — Никита.

### Поток A — ядро бэкенда

Отвечает за:

- сущности, репозитории и Liquibase;
- DTO и REST-контроллеры согласованного контракта;
- транзакцию завершения Квеста;
- расчёт XP, уровня, награды и урона;
- unit- и integration-тесты бизнес-логики.

Основная область: `backend/src/main/**`, кроме пакетов `integration` и `realtime` после создания их границ.

### Поток B — интерфейс

Отвечает за:

- TypeScript-типы, точно повторяющие `CONTRACTS.md`;
- API-функции и временный fixture;
- Dashboard, Квесты, персонажа и босса;
- последовательность реакций и финальное состояние UI;
- typecheck, build и визуальную проверку.

Основная область: `frontend/src/api`, `pages`, `components`, `css` и локальные UI-ассеты.

### Поток C — доставка событий и демо

Отвечает за:

- демонстрационные reset/complete адаптеры поверх сервиса A;
- проверку полного сценария и повторного события;
- будущую границу GitHub webhook;
- необязательный realtime-канал после готовности REST.

Основная область: backend-пакеты `integration`/`realtime`. Фронтенд-файлы C меняет только после согласования точки подключения с B.

Поток C не рассчитывает XP, уровни или урон и не изменяет доменные сущности напрямую.

## Решение по обновлению UI

- Первый MVP использует ответ `POST .../complete` и сразу применяет `ProgressionResult`.
- Это обязательный и демонстрационно безопасный путь.
- WebSocket не блокирует MVP и проверяется только после работающей REST-вертикали.
- Если WebSocket добавляется, он отправляет тот же `ProgressionResult`, без второго контракта.
- При ошибке realtime UI перечитывает `GET /api/demo/state`.

## Общие и конфликтные файлы

| Область | Правило изменения |
|---|---|
| `CONTRACTS.md` и общие DTO | Менять совместным решением; один редактор за раз |
| Liquibase master и схема | Поток A |
| Сервис прогресса и сущности | Поток A; C только вызывает публичный метод |
| `pom.xml`, `application.yaml` | A и C согласуют; редактирует один поток за раз |
| Frontend API-типы и Axios | Поток B; C использует готовую границу |
| Router, layout, глобальные стили | Поток B |
| `package.json`, Quasar config | Не менять без конкретной необходимости и согласования |
| Документация этапа | Один редактор за раз, решения принимаются совместно |

Доверие внутри команды не отменяет это разделение: оно предотвращает технические merge-конфликты, а не ограничивает участников.

## Ветки и интеграция

Рекомендуемые ветки: `feature/mvp-backend`, `feature/mvp-frontend`, `feature/mvp-integration`. При использовании AI — отдельный worktree на задачу.

Порядок интеграции:

1. A создаёт доменную границу и проверяемый сервис.
2. B параллельно собирает UI на fixture из `CONTRACTS.md`.
3. C подключает демо-адаптер только к публичному сервису A.
4. B заменяет fixture живым REST API.
5. Команда проверяет reset -> complete -> повтор -> reset.
6. Только после этого C может добавить WebSocket или реальный GitHub webhook.

## Критерий завершения Этапа 0

- Контракт 0.1 зафиксирован и одинаково читается Java и TypeScript сторонами.
- У каждого потока есть отдельная область и понятные точки пересечения.
- REST-ответ выбран обязательным способом обновления UI.
- Детерминированный reset/complete остаётся запасным путём демонстрации.
- Параллельную реализацию можно начинать без изменения контракта.
