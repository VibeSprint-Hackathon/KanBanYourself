# Сценарий демонстрации

## История

Аудитория должна понять одну причинную цепочку:

`реальная разработка -> завершение Квеста -> личный прогресс -> командный прогресс`

Показывать один сильный сценарий, а не экскурсию по всем страницам.

## Подготовленное состояние

- Игрок: Уровень 4, 920/1000 XP, базовая косметика.
- Квест: `Исправить проверку платежа`, `IN_PROGRESS`, награда 180 XP.
- Босс: осталось 180 HP.
- Следующая награда: одна редкая косметика на Уровне 5.

Способ хранения XP зависит от контракта Этапа 0; значения выше обязательны только для показа.

## Идеальный сценарий

1. Открыть Dashboard и кратко показать Квест, персонажа, XP и босса.
2. Вызвать событие merge PR через живой GitHub-путь, если он многократно проверен.
3. Квест переходит в `DONE`, появляется `Квест завершён`.
4. `+180 XP` заполняет шкалу от 920 до 1100 общего прогресса.
5. Персонаж реагирует, достигает Уровня 5 и получает косметику.
6. Босс получает 180 урона и побеждён.
7. Открывать ссылку Квеста только если это добавляет уверенности и не тормозит рассказ.

## Живой путь

Предпочтительный финальный путь:

`PR merged -> GitHub webhook -> адаптер -> сервис прогресса Spring -> UI-событие`

Использовать на презентации только после повторной репетиции в той же сети и репозитории.

## Надёжный запасной путь

Видимый или управляемый ведущим детерминированный триггер отправляет ту же команду завершения в Spring Boot. Она проходит через ту же транзакцию, что и живой адаптер. UI показывает идентичный результат.

Нужен детерминированный prepare/reset или документированный seed запуска, чтобы репетиция и восстановление не требовали редактирования БД.

## Необязательные внешние зависимости

Презентация должна работать без:

- доступности GitHub и сроков доставки webhook;
- CI, merge queues и реального merge PR;
- n8n;
- внешнего AI;
- доставки финальных ассетов художником;
- интернета.

Стабильные ассеты хранятся локально, запасной путь доступен даже при работающей интеграции.

## Проверка перед показом

- Запустить подготовленное состояние без редактирования БД.
- Убедиться, что один триггер даёт ровно 180 XP и урона.
- Запустить второй раз: награда не повторяется.
- Финальные данные верны при пропущенной/сокращённой анимации.
- После перезагрузки состояние остаётся завершённым.
- Сбросить и повторить сценарий минимум трижды.
- Проверить разрешение, масштаб браузера, ассеты и сообщение при недоступном бэкенде.
- Записать точное запасное действие для ведущего.

## Критерий успеха

Полная реакция надёжна, понятна без пояснений и достаточно быстра для питча. Реальный GitHub ценен, но не должен угрожать детерминированной истории.
