# Фронтенд

## Текущее состояние

Фронтенд — шаблон Vue 3 + TypeScript + Quasar. Есть один layout, страница проверки бэкенда, hash routing, строгий TypeScript, Axios-клиент `src/api/http.ts` с базой `/api` и STOMP-клиент прогресса. Pinia установлена, но store не создан.

## Основные страницы

- `/` Dashboard: главная отполированная страница и сцена демонстрации.
- `/quests` Квесты: три колонки `TODO`, `IN_PROGRESS`, `DONE`.
- `/character` Персонаж/Профиль: крупный персонаж, уровень, титул, косметика и следующая награда.

При нехватке времени Dashboard может включить основную доску и сводку персонажа; отдельные маршруты — удобство после MVP.

## Группы компонентов

- `dashboard`: игрок, активный Квест, активность, панель рейда/босса.
- `quests`: доска, колонка, карточка, необязательный dialog/drawer деталей.
- `character`: отображение кадров, XP/уровень, косметика и награда.
- `progression`: сообщение о завершении и последовательность анимаций.
- `shared`: компактные loading/error состояния и игровые оболочки карточек.

Не строить отдельную дизайн-систему в рамках хакатона.

## Состояние и поток данных

1. Типизированный API-модуль загружает read-модель демо.
2. Страница отображает серверные данные как локальное состояние.
3. Ответ завершения или realtime-событие применяет один типизированный `ProgressionResult`.
4. UI-последовательность меняет временное состояние анимации и завершается серверными значениями.

Pinia нужна только если Dashboard, Квесты и realtime действительно делят состояние. Для первой одностраничной вертикали достаточно composable.

## API-слой

- Сохранить существующий Axios instance.
- Типизированные функции и DTO держать вне Vue-компонентов.
- Не дублировать расчёты бэкенда и не разбрасывать HTTP-вызовы по компонентам.
- Повторные/устаревшие события применять идемпотентно по финальным данным сервера или id события.

## Состояние персонажа

Значения бэкенда: `idle`, `coding`, `happy`, `level-up`. Фронтенд сопоставляет их с доступными кадрами и управляет временем. При отсутствии ассетов использовать один аккуратный placeholder без изменения API.

## Realtime

`src/boot/realtime.ts` запускает единственный клиент при старте приложения. `src/realtime/progression.ts` подключается к `/ws`, подписывается на `/topic/progression` и передаёт типизированный `ProgressionResponse` подписчикам. Для локальной разработки адрес по умолчанию — `ws://localhost:8080/ws`; переопределение задаётся в `VITE_WS_URL`.

Компонент или composable подписывается через `progressionRealtime.subscribe(handler)` и вызывает возвращённую функцию при размонтировании. Инициирующий экран всё равно сначала применяет REST-ответ. Realtime нужен для других открытых экранов; после ошибки или переподключения они перечитывают `GET /api/demo/state`.

## Разделение области

MVP:

- Dashboard, минимальные колонки Квестов, XP/уровень, персонаж, босс и последовательность завершения.
- Достаточная адаптация под экран презентации.

Полировка после MVP:

- Отдельные маршруты Квестов/Профиля, переходы, журнал активности, хорошие loading/error состояния.

Дополнительные возможности:

- Больше косметики, достижения, sharing и интерфейс браузерного компаньона.

## Вероятное владение

- `src/pages`, `src/components/dashboard`, `src/components/progression`: владелец основного UI.
- `src/api` и общие DTO-типы: владелец контрактов совместно с бэкендом.
- `src/css`, layout, router и точка входа Pinia: общие конфликтные области, редактировать последовательно.
