# Система документации

## Цель

Документация должна помогать команде быстро начать конкретную задачу и не требовать чтения всей истории проекта. Мы храним отдельно:

- актуальные знания о продукте и системе;
- рабочий контекст текущего этапа;
- краткий результат завершённых этапов.

Документация не является дневником разработки. Ход работы остаётся в задачах, ветках и истории Git.

## Структура хранения

```text
AGENTS.md                         общие правила и маршруты чтения
docs/
├── PRODUCT.md                    продукт и аудитория
├── MVP.md                        границы первого результата
├── ARCHITECTURE.md               общая схема и контракты между частями
├── BACKEND.md                    правила и ответственность бэкенда
├── FRONTEND.md                   правила и ответственность фронтенда
├── INTEGRATIONS.md               GitHub, realtime, n8n и внешние события
├── DESIGN.md                     визуальное направление и ассеты
├── COLLABORATION.md              владение, ветки и интеграция команды
├── DEMO.md                       сценарий показа и запасной путь
├── IMPLEMENTATION_PLAN.md        порядок реализации и приоритеты
├── DOCUMENTATION.md              правила из этого документа
├── assets/                       только используемые документацией файлы
└── stages/                       контекст и итоги этапов разработки
    ├── 00-contracts/
    │   └── README.md
    ├── 01-mvp/
    │   └── README.md
    ├── 02-polish/
    │   └── README.md
    └── 03-selected-stretch/
        └── README.md
```

Папки этапов создаются только при начале соответствующего этапа. Пустые папки и документы «на будущее» не нужны.

## Два уровня документации

### Постоянные документы

Файлы в корне `docs/` описывают только текущее согласованное состояние. В них нет отчётов по дням, списков выполненных коммитов и подробной истории обсуждений.

Если решение изменилось, постоянный документ обновляется. Старое описание не сохраняется рядом «для истории» — история уже есть в Git.

### Документы этапов

`docs/stages/<номер>-<название>/README.md` отвечает только на вопросы конкретного этапа:

- какой результат должен быть получен;
- что входит и не входит в этап;
- кто владеет направлениями и общими файлами;
- какие решения ещё открыты;
- как проверить результат;
- что передаётся следующему этапу.

Завершённый этап не редактируется из-за обычных будущих изменений. Исправлять его можно только для устранения фактической ошибки с явной пометкой.

## Этапы проекта

### `00-contracts`

Содержит согласованные перед разработкой решения: JSON-примеры, enum, формулы XP/урона, правила повторного события, владельцев контрактов и выбранный способ обновления UI.

После реализации код и тесты становятся источником истины для точных DTO. README этапа сохраняет только итог решения и ссылки на соответствующие файлы кода.

### `01-mvp`

Объединяет параллельные потоки A, B и C. README фиксирует общий результат, владельцев, точки интеграции, критерии приёмки и найденные ограничения.

Подробности реализации не копируются из `BACKEND.md`, `FRONTEND.md` или кода. При необходимости допускается один дополнительный файл на действительно большой общий контракт.

### `02-polish`

Хранит только список выбранной полировки, результаты репетиций и критерии готовности финального показа. Ошибки ведутся в задачах, а не списком в Markdown.

### `03-selected-stretch`

Создаётся только после выбора одной дополнительной возможности. Название папки можно уточнить, например `03-browser-companion`. Не создавать отдельные папки для идей, которые не были выбраны.

## Жизненный цикл этапа

### Перед началом

1. Создать папку этапа и один `README.md` по шаблону ниже.
2. Указать владельца каждого направления и конфликтных файлов.
3. Сослаться только на необходимые постоянные документы.
4. Зафиксировать критерии завершения до реализации.
5. Поставить статус `ACTIVE`.

### Во время работы

- Обновлять только решения, область и критерии, которые реально изменились.
- Не вести поминутный журнал и не копировать комментарии из задач.
- Новое постоянное правило сразу переносить в профильный корневой документ.
- В README этапа оставлять ссылку на источник истины, а не копию текста.
- Изменение общего контракта сначала согласовать с его владельцами.

### При завершении

1. Записать фактически полученный результат.
2. Указать выполненные проверки и известные ограничения.
3. Перенести устойчивые знания в профильные постоянные документы.
4. Удалить временные предположения и устаревшие черновики.
5. Записать входные данные для следующего этапа.
6. Поставить статус `DONE`.

## Минимальный шаблон README этапа

```md
# Этап NN — название

Статус: PLANNED | ACTIVE | DONE
Владелец этапа: имя

## Результат этапа
Одно проверяемое предложение.

## Область
- Входит: ...
- Не входит: ...

## Владение
| Направление | Владелец | Файлы/каталоги |
|---|---|---|

## Решения и открытые вопросы
- Решено: ...
- Открыто: ...

## Проверка
- Команда или ручной сценарий: ожидаемый результат.

## Передача дальше
- Реализовано: ...
- Ограничения: ...
- Следующий шаг: ...
```

## Где фиксировать изменения

| Изменение | Источник истины |
|---|---|
| Цель продукта или аудитория | `PRODUCT.md` |
| Граница первого релиза | `MVP.md` |
| Системный поток или общий контракт | `ARCHITECTURE.md` |
| Правило бэкенда/фронтенда | `BACKEND.md` / `FRONTEND.md` |
| Интеграция или внешний event | `INTEGRATIONS.md` |
| Визуальное правило или ассет | `DESIGN.md` |
| Командный процесс | `COLLABORATION.md` |
| Сценарий презентации | `DEMO.md` |
| Порядок и приоритет работ | `IMPLEMENTATION_PLAN.md` |
| Область, решение и итог конкретного этапа | `stages/<этап>/README.md` |
| Точная реализованная DTO/формула | код и тесты; документация только ссылается |

## Имена и формат файлов

- Имена файлов и каталогов — на английском языке.
- Содержимое документации — на русском языке.
- Постоянные документы используют `UPPER_SNAKE_CASE.md`; README этапа сохраняет стандартное имя.
- Папки этапов: двузначный номер и `kebab-case`.
- Каждый Markdown-файл — менее 200 строк.
- Диаграммы и изображения хранятся в `docs/assets/<topic>/` и должны использоваться хотя бы одним документом.
- Экспортированные отчёты, логи, сборки и временные скриншоты в `docs/` не хранятся.

## Правило создания дополнительного файла этапа

Сначала расширяется README этапа. Дополнительный файл создаётся только если у него отдельная аудитория и назначение, а README приближается к лимиту. Допустимые примеры: `CONTRACTS.md` или `VERIFICATION.md`. Файлы `NOTES.md`, `MISC.md` и `TODO.md` без чёткой ответственности запрещены.
