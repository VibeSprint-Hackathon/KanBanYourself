# Интеграции

## Принцип владения

Интеграция и оркестрация могут находиться вне ядра, но Spring Boot остаётся источником истины для переходов Квестов, XP, уровней, наград и урона рейду.

## GitHub Issues

На MVP поддерживается только интеграция с GitHub Issues.

Целевой поток:

```text
GitHub Issue webhook
        ↓
GitHub adapter
        ↓
нормализованная команда Spring
        ↓
изменение прогресса
        ↓
обновление UI
```

Интеграция должна поддерживать только события, связанные с GitHub Issue. Pull Request, review, commits, repository events и другие типы GitHub-событий в MVP не поддерживаются.

### Поддерживаемое событие

Основное событие MVP — **закрытие связанного GitHub Issue**.

При получении события:

1. webhook-обработчик проверяет тип события;
2. извлекает и нормализует идентификаторы GitHub Issue;
3. определяет связанный Квест;
4. передаёт нормализованную команду в тот же сервис, который используется демо-триггером;
5. Spring Boot применяет правила прогресса;
6. результат становится доступен через REST и realtime-механизм.

Неподдерживаемые события должны отклоняться до передачи в доменную логику.

Перед публикацией реального webhook идентификатор доставки GitHub должен использоваться для защиты от повторной обработки одного и того же события.

Spring Boot не должен зависеть от формата GitHub webhook внутри доменной логики. GitHub adapter отвечает за преобразование внешнего события в внутреннюю команду.

## Связь Квеста с GitHub Issue

MVP требует необязательную внешнюю ссылку у Квеста.

Минимальная модель:

```text
provider
repository
issueNumber
```

Для GitHub `provider` имеет значение `github`.

Пример:

```json
{
  "provider": "github",
  "repository": "owner/repository",
  "issueNumber": 42
}
```

Связь означает:

> закрытие указанного GitHub Issue завершает связанный Квест.

Универсальную модель интеграций и провайдеров заранее проектировать не требуется. На MVP достаточно структуры, необходимой для GitHub Issues.

Один GitHub Issue не должен повторно выдавать прогресс при повторной доставке webhook.

## Детерминированный демо-триггер

Демо должно работать без GitHub.

Надёжный путь демонстрации — бэкенд-адаптер, отправляющий ту же нормализованную команду, которую использует GitHub adapter.

```text
Demo trigger
    ↓
нормализованная команда
    ↓
Spring progression service
```

Демо-триггер не изменяет XP, награды или состояние рейда напрямую. Все изменения выполняются через тот же сервис и правила, что и для реального GitHub Issue.

Если действие отображается в UI, его следует обозначать как демо-событие, а не как ручное изменение состояния Квеста.

`POST /api/demo/reset` реализован как атомарное восстановление полного seed и возвращает агрегированное состояние.

Защита endpoint не входит в MVP локального запуска.

## Realtime

Бэкенд предоставляет STOMP endpoint `/ws` и topic `/topic/progression` через встроенный простой broker.

Payload совпадает с REST `ProgressionResponse`; отдельного realtime-контракта нет.

Vue-клиент подключается при запуске приложения из:

```text
src/boot/realtime.ts
```

Общий клиент находится в:

```text
src/realtime/progression.ts
```

Клиент:

- поддерживает одну STOMP-сессию;
- автоматически переподключается через 3 секунды;
- позволяет отдельно подписаться на прогресс и состояние соединения.

В разработке адрес по умолчанию:

```text
ws://localhost:8080/ws
```

Его можно заменить через `VITE_WS_URL`.

Production-клиент строит `/ws` на своём хосте, но backend сейчас разрешает Origin только `localhost` и `127.0.0.1`. Внешний deployment потребует отдельной настройки CORS/Origin.

Событие прогресса отправляется после возврата транзакционного сервиса и только для `applied=true`.

Повторное завершение Квеста не публикуется как новое событие прогресса.

Ошибка доставки realtime-события логируется, но не превращает уже сохранённое REST-завершение в ошибку.

Порядок запасных вариантов:

1. ответ операции обновляет инициирующий UI;
2. после ошибки или переподключения перечитывается состояние;
3. короткий polling используется только если WebSocket недоступен.

Клиент подключён без изменений визуальной части потока B, но Dashboard пока не применяет его сообщения. В I1 composable должен подписаться через:

```text
progressionRealtime.subscribe(...)
```

После ошибки или восстановления соединения он перечитывает:

```text
GET /api/demo/state
```

## Границы GitHub-интеграции

В MVP GitHub интеграция ограничена Issues.

Не входят:

- Pull Requests;
- Pull Request reviews;
- commits;
- repository events;
- GitHub Actions;
- merge queues;
- автоматизация через n8n;
- AI-предобработка GitHub-событий;
- браузерное расширение.

Эти возможности могут быть добавлены после стабилизации базового сценария.

## Безопасность демонстрации

Презентация не должна зависеть от GitHub или сетевых задержек.

Реальная интеграция с GitHub Issues дополняет, но не заменяет путь из [DEMO.md](DEMO.md).

## Будущая связь Raid с GitHub Milestone

Raid существует и проходит lifecycle независимо от GitHub. Текущее nullable `externalReference` позволяет сохранить URL или номер Milestone без зависимости домена от webhook payload.

Будущий адаптер должен преобразовывать события Milestone в нормализованные команды create/link/complete и вызывать Raid service. Формат GitHub, запросы к API и решение об автоматическом завершении остаются в адаптере; `ProgressionService` работает только с внутренним `ACTIVE` Raid.

Демонстрация должна быть полностью воспроизводима локально через демо-триггер даже при отсутствии доступа к GitHub.
