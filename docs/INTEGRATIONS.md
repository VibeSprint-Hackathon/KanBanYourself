# Интеграции

## Принцип владения

Интеграция и оркестрация могут находиться вне ядра, но Spring Boot остаётся источником истины для переходов Квестов, XP, уровней, наград и урона рейду.

## GitHub

Целевой поток после MVP:

```text
GitHub webhook -> адаптер (напрямую или через n8n) -> команда Spring
               -> результат прогресса -> обновление UI
```

Начать с одного ценного события: merge pull request завершает связанный Квест. Более широкая поддержка issues, назначений, review и репозиториев — дополнительная возможность.

Webhook-обработчик проверяет событие, нормализует идентификаторы, отклоняет неподдерживаемые действия и передаёт команду в тот же сервис, что использует демо-триггер. Перед публикацией реального webhook идентификатор доставки должен защищать от дублей.

## Связь Квеста с issue/PR

MVP требует только необязательную внешнюю ссылку у Квеста. Точная модель не решена; минимальный вариант — provider/repository/number. Не проектировать универсальную модель провайдеров заранее.

Для реального GitHub-сценария выбрать: Квест связан с issue и завершается закрывающим PR либо напрямую связан с PR. Прямая связь проще; закрытие issue через PR убедительнее.

## Детерминированный демо-триггер

Надёжный путь демо — бэкенд-адаптер, отправляющий ту же нормализованную команду, что и GitHub. Он не изменяет XP или рейд напрямую. Если действие видно в UI, обозначить его как демо-событие, а не ручной workflow Квеста.

`POST /api/demo/reset` реализован как атомарное восстановление полного seed и возвращает агрегированное состояние. Защита endpoint не входит в MVP локального запуска.

## Realtime

Бэкенд предоставляет STOMP endpoint `/ws` и topic `/topic/progression` через встроенный простой broker. Payload совпадает с REST `ProgressionResponse`; отдельного realtime-контракта нет.

Vue-клиент подключается при запуске приложения из `src/boot/realtime.ts`. Общий клиент находится в `src/realtime/progression.ts`, поддерживает одну STOMP-сессию, автоматически переподключается через 3 секунды и позволяет подписаться отдельно на прогресс и состояние соединения. В разработке адрес по умолчанию — `ws://localhost:8080/ws`; его можно заменить через `VITE_WS_URL`. Production-клиент строит `/ws` на своём хосте, но backend сейчас разрешает Origin только `localhost` и `127.0.0.1`: внешний deployment потребует отдельной настройки.

Событие отправляется после возврата транзакционного сервиса и только для `applied=true`. Повторное завершение не отправляется. Ошибка доставки логируется, но не превращает уже сохранённое REST-завершение в ошибку.

Порядок запасных вариантов:

1. ответ завершения обновляет инициирующий UI;
2. после ошибки/переподключения перечитывается состояние;
3. короткий polling — только если WebSocket нельзя использовать.

Клиент подключён без изменений визуальной части потока B, но Dashboard пока не применяет его сообщения. В I1 composable должен подписаться через `progressionRealtime.subscribe(...)`; после ошибки или восстановления соединения он перечитывает `GET /api/demo/state`.

## n8n

n8n необязателен и подходит для маршрутизации webhook, AI-предобработки, уведомлений и автоматизации демо. Он не хранит авторитетный прогресс и не считает награды. Прямой GitHub -> Spring предпочтителен, если он проще.

## Браузерный компаньон

Расширение браузера — дополнительная возможность. Оно использует те же read/event контракты и не содержит правил прогресса. Не начинать до стабилизации Dashboard.

## Безопасность демонстрации

Презентация не должна зависеть от GitHub, CI, merge queues, n8n, внешнего AI или сетевых задержек. Реальная интеграция дополняет, но не заменяет путь из [DEMO.md](DEMO.md).

## Открытые решения

- Прямой webhook или n8n после MVP.
- Прямая связь с PR или issue, закрытый PR.
- Проверка webhook и место развёртывания для финального показа.
- Требуется ли realtime-обновление второго клиента.
